## Défauts trouvés (à décider)

1. **STD-1.1 non respectée** : `io::println("x")` **sans** `use std::io;`
   compile et s'exécute (vérifié : `run` → `x`, code 0), alors que STD-1.1
   (MUST) exige le `use`. Plusieurs cas existants en dépendent
   (`ownership/mutable-places-accept-writes`, `cli/abi-emit-rust-*`,
   `cli/check-json-spans-utf16-crlf`). Deux voies : corriger le checker
   (rupture pour ces programmes, COMPAT-2.4) ou amender STD-1.1. **Non
   rattachée, rien modifié.**
2. **DIAG-5.5** : le refus d'une dépendance nommée `std` (`E-RES-CONFLICT`)
   s'affiche `--> <unknown>`, sans span, alors que DIAG-5.5 exige un span
   d'au moins un scalaire (le span du nom dans `ravum.toml` existe). Non
   rattachée.
3. **DIAG-6.4, moitié `= help:`** : aucun diagnostic ne porte d'aide ; la
   règle est vraie par absence de producteur. Rattachée pour la moitié
   `note`, limite écrite dans le cas.
4. **Registre** (pré-existant, de ma V1) : les codes `E-CON-EFFECT`,
   `E-CON-NONCOPY`, `E-CON-UNSUPPORTED`, `E-CON-FIELD-WRITE` (RFC-CONTRACTS-1
   et RFC-INVARIANTS-1, `ACCEPTED`) étaient émis mais absents de
   `diagnostics.md` §3 : `tools/tests/test_feature_table.py` échouait.
   **Corrigé** : §3.6.3 ajoutée, codes ajoutés au snapshot (ajout seul,
   DIAG-9.1). `tools/tests` : 90/90.
5. **Phase JSON** (pré-existant, de ma V1) : `check --json` rangeait ces
   quatre codes dans la phase `tool` (`phase_for_code`, branche par défaut).
   **Corrigé** dans `crates/ravum-lang-cli/src/json.rs` : `effects` pour
   `E-CON-EFFECT`, `types` pour `E-CON-NONCOPY` et `E-CON-FIELD-WRITE`,
   `parse` pour `E-CON-UNSUPPORTED` ; vérifié par
   `every_registered_code_reports_its_registry_phase`. (Hors du périmètre
   strict de L3, mais nécessaire pour que le registre corrigé ne casse pas
   la CI.)
