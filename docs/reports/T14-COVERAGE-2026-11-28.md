# T14 / T15 — couverture de l'IR et moteur JIT sur les paquets (2026-11-28)

Statut : `TESTED` (Linux, `rustc 1.95.0`). Base : `dev` @ `f604068`.
Branche : `ir-coverage-t14`. Aucun gate n'est déclaré `PASS` ici : T14

## Pourquoi
Décision du responsable (2026-11-28) : le moteur de développement (IR + JIT,
V2-G7) doit porter une vraie application et ne recompiler que ce qui change.
`apps/ledger` (branche d'essai, hors `dev`) sert de cible.

## Changements
1. **Types opaques du runtime** (`Future`, `Sender`, `TcpListener`…) : refus
   `Unsupported("opaque runtime type …")` au lieu d'un faux
   `MissingFact`, qui se lisait comme une erreur interne.
2. **IR 1.9 : `char`** (point de code, `u32` dans l'IR ; le vérificateur
   interdit l'arithmétique) : littéraux avec échappements, `match` sur
   `char`, comparaisons, `as u32`, `String::push`, `char::to_string`
   (y compris à travers une référence), `Vec<char>`, `Option<char>`,
   `Map<char, _>`. Deux opérations de tas additives : `StrPushChar`,
   `StrOfChar` ; un mot qui n'est pas un scalaire Unicode est une faute,
   jamais un caractère de remplacement.
3. **`&v[i]` partagé d'un élément scalaire** : adresse d'une copie, comme
   `&x` (la vérification interdit d'écrire au travers) ; `&mut` reste refusé.
4. **`Option::ok_or`, `Result::ok`, `Result::err`** (charges scalaires, texte
   et agrégats ; argument évalué quelle que soit la variante, O1).
5. **Modules** : modules en ligne et fichiers développés par le chargeur,
   aplatis ; homonymes distincts, chemins `super::`/`crate::` ; un `main`
   dans un module n'est pas l'entrée (F-MOD-011, vérifié explicitement).
6. **Abaissement par point d'entrée** (`lower_for`, `compile_source_for`,
   `lower_checked_for`) : seules les fonctions atteignables depuis les
   entrées doivent être couvertes. Une fonction non atteignable devient un
   bouchon qui s'arrête avec la raison ; l'atteignabilité est exacte (pas de
   valeur fonction), donc aucun bouchon ne s'exécute. Une fonction non
   couverte **atteinte** est refusée en la nommant (`… (in \`argc\`)`).
   `lower` (strict) est inchangé.
7. **`watch --backend jit` sur un paquet à modules** : tous les fichiers de
   `src/` surveillés (dates et tailles, puis contenus) ; chargement comme le
   serveur de langage (cache d'analyse, identifiants de fichier stables),
   vérification incrémentale du paquet (T13), puis **seules les fonctions
   modifiées** recompilées par le moteur. Entrées abaissées : l'entrée de
   session plus `init`/`step`/`migrate` de la racine. Un paquet d'un seul
   fichier garde le mode mono-fichier (racine vérifiée comme bibliothèque),
   à l'identique.

## Écarts et décisions à prendre (non tranchés ici)
- **`assert` : la spec et la voie `rustc` divergent.** STD-8.1 :
  `panic: assertion failed: <file>:<line>:<col>` ; la voie `rustc` affiche
  `panic: assertion failed at src/main.rv:2` (ni colonne, « at »). À
  trancher avant d'ajouter `assert`/`assert_eq` à l'IR (qui devra en plus
  connaître le fichier source).
- **E/S hôte dans l'IR** (`fs`, `env`, `process`, `thread`, `net`) : refus
  voulus par conception (V2-L2). Pour qu'une application UI tourne sur le
  moteur, son point d'entrée n'en a pas besoin (la fenêtre est l'hôte) ;
  `apps/ledger` les utilise dans `main` et `report::build` (threads), qui
  restent donc hors du moteur. Les ouvrir demanderait des appels hôte typés :
  conception à proposer.
- `pow` et libm : refus voulus (MACH-5.4, hors noyau vérifiable).
